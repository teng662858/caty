## 0. 先确认"选哪个 Node 运行时"（结论已定，你只需要知道）

**用 `digidem/nodejs-mobile` 的 Node **24** 版，不要用官方 NodeMobile 的 18.20.4。**

一句话理由：你的 bundle 在 iOS 无 JIT 环境下没有 `WebAssembly`，而 Node 的 `fetch()` 是拿
WebAssembly 实现的 → **官方 Node 18 在 iOS 上 `fetch` 直接是坏的**（源里到处在用），
而且 Node 18 没有编译缓存（无 JIT 下最值钱的优化）。Node 24 这条线两个问题都解决了。

（出处与细节见 `docs/04-conversation-log.md` 本轮记录；有真机验证的第三方案例。）

**开工前先在 Windows 上跑一次桌面预演**（不下载、不执行任何第三方代码，10 秒）：

```bash
cd /d/Zcode/Catys && node tools/host/p2-selftest.mjs
```

应该看到最后一行 `✓ P2 链路自检通过`。
👉 如果这行没出现：**把整段输出贴给我**，别继续往下走。

## 1. 下载 NodeMobile.xcframework（在 Mac 上做）

> 💡 **没有 Mac？** 那就不用走这一步 —— 改用 [09-没有Mac也能装到手机.md](09-没有Mac也能装到手机.md)，
> 那台 GitHub 的 macOS 机器会自己下载这个框架并校验 sha256。本操作卡是"有 Mac"时用的。

1. 用 Safari 打开这个页面（Mac 上）：

   ```
   https://github.com/digidem/nodejs-mobile/releases/tag/v24.20.0-0
   ```

   > 国内直连 GitHub 下载很慢（实测约 16 KB/s）。下不动就用加速前缀：
   > `https://gh-proxy.com/https://github.com/digidem/nodejs-mobile/releases/download/v24.20.0-0/nodejs-mobile-ios-lite-24.20.0-0.zip`
   > （约 1 MB/s）

2. 在下面的 **Assets** 里点这个文件名下载：

   ```
   nodejs-mobile-ios-lite-24.20.0-0.zip        （26,737,415 字节，lite 版更省内存，够我们所有功能）
   ```

   > 如果 lite 版下载不了，改成 `nodejs-mobile-ios-24.20.0-0.zip`（全量版）也完全可以。
   > 想核对下载是否完整：这个 zip 的 sha256 应该是
   > `991283d8579eee225142da2bf4a897dd7d831e8b5a496a1f247fca665bc1d705`

3. 双击解压。解压出来的文件夹里找到：

   ```
   NodeMobile.xcframework
   ```

   （它可能在子文件夹里，比如 `nodejs-mobile-v24.20.0-0/out_ios/` 下面。）

4. 把这个 `NodeMobile.xcframework` 放到你的工程目录里，建议放在：

   ```
   <工程目录>/Frameworks/NodeMobile.xcframework
   ```

   没有 `Frameworks` 文件夹就自己新建一个（和 `Caty.xcodeproj` 同级）。

✅ 验收：`NodeMobile.xcframework` 里有 `ios-arm64` 与 `ios-arm64-simulator` 两个文件夹（实测就是这个组合）。
⛔ 只有 `macos-arm64` 之类没有 `ios-` 开头的 → 你下成 macOS 版了，回第 2 步重下。
📌 Intel Mac 注意：模拟器片只有 arm64（没有 x86_64），所以 Intel Mac 上跑模拟器会链接失败 —— 直接用真机即可。

## 2. 把代码放进工程（5 分钟，纯拖拽）

我给你的 **`dist/Caty-P2P3-代码包.zip`** 解压后长这样（这个包也在 `ios/` 目录里，内容一致）：

```
Sources/                      ← 全部 Swift 代码
Resources/                    ← bootstrap.js、打桩 bundle、Info.plist
Caty-Bridging-Header.h
```

1. 把 `Sources`、`Resources` 两个**文件夹**和 `Caty-Bridging-Header.h`，整个拷到你的工程目录
   （就是有 `Caty.xcodeproj` 的那一层，和 Xcode 自动建的 `Caty/` 文件夹并列）。

2. 打开 Xcode，在左侧导航栏的项目名上 **右键 → Add Files to "Caty"…**

3. 在弹出的窗口里：
   - 选中 `Sources`、`Resources`、`Caty-Bridging-Header.h` 这三项；
   - 顶部选 **Create groups**（不是 Create folder references）；
   - **不要**勾 "Copy items if needed"（文件已经在工程里了）；
   - 底部 **Add to targets 勾上 Caty**；
   - 点 Add。

4. **删掉 Xcode 自动生成的两个文件**：在左侧导航里选中 `CatyApp.swift` 和 `ContentView.swift`
   （Xcode 建工程时自己生成的，在 `Caty/` 文件夹里）→ 右键 **Delete** → **Move to Trash**。

   > 为什么必须删：我给的 `Sources/App/CatyApp.swift` 里也有 `@main`，两个 `@main` 会编译报错
   > （报错原文长这样：`'main' attribute cannot be used in a module that contains top-level code` 或
   > `multiple 'main' ...`）。

5. **把 `Info.plist` 从 target 里排除**：左侧选中 `Resources/Info.plist` → 右边 **File Inspector**
   （最右边那个像纸一样的图标）→ 把 **Target Membership** 里 `Caty` 的勾**去掉**。

   > 它是给"Build Settings 里的 Info.plist File"用的，不需要被复制进 App 包；勾着会有一条警告。

✅ 验收：左侧能看到 `Sources/`（里面 App、Runtime、Features）和 `Resources/` 两组文件，
`Resources` 里有 `bootstrap.js`、`stub-bundle.index.js`、`stub-bundle.index.config.js`、`Info.plist`。

## 3. 把 NodeMobile 链接并嵌入（最容易报错的一步）

1. 在你工程目录里，把 `Frameworks/NodeMobile.xcframework` **拖进 Xcode 左侧导航**（松手时别落在别的组里）。
   弹窗里：**Copy items if needed 不勾**、**Add to targets 勾 Caty**、点 Finish。

2. 左侧点最上面的项目名 → 中间选 **TARGETS: Caty** → **General** 标签 →
   往下找 **Frameworks, Libraries, and Embedded Content**。

3. 确认列表里有 `NodeMobile.xcframework`，并且它右边的下拉是：

   ```
   Embed & Sign
   ```

   没有的话：点下面的 **+** → 选 NodeMobile.xcframework → Add，再把下拉改成 **Embed & Sign**。

✅ 验收：这一栏是 `NodeMobile.xcframework | Embed & Sign`。
⛔ 报 `Undefined symbol: _node_start` → 说明没链接上，回第 1 步重做。
⛔ 报 `Library not loaded: @rpath/NodeMobile.framework/...` → 说明只 Link 没 Embed，把下拉改成 **Embed & Sign**。

## 4. 改 4 个 Build Settings（照着抄，别自己发挥）

左侧项目名 → **TARGETS: Caty** → **Build Settings** 标签 → 左上角把 **All** 和 **Combined** 都选上，
然后用右上角搜索框逐个改：

| 搜索这个词 | 设置项 | 改成 |
|---|---|---|
| `Info.plist File` | Info.plist File (`INFOPLIST_FILE`) | `Resources/Info.plist` |
| `Generate Info` | Generate Info.plist File (`GENERATE_INFOPLIST_FILE`) | **No** |
| `Bridging` | Objective-C Bridging Header (`SWIFT_OBJC_BRIDGING_HEADER`) | `Caty-Bridging-Header.h` |
| `Strict Concurrency` | Swift Strict Concurrency Checking | **Minimal** |

再确认两个（一般已经是对的）：

| 搜索这个词 | 设置项 | 值 |
|---|---|---|
| `Deployment Target` | iOS Deployment Target | `17.0` 或更高 |
| `Swift Language` | Swift Language Version (`SWIFT_VERSION`) | **Swift 5**（不要选 Swift 6） |

> 为什么要设 Strict Concurrency = Minimal / Swift 5：我的代码用的是最稳的写法，
> 在 Swift 6 的严格并发模式下会有编译错误。这是有意的取舍 —— 先把功能跑通。

✅ 验收：`Cmd+B`（只编译，不运行）能 Build Succeeded。
⛔ 报 `Cannot find 'node_start' in scope` → 桥接头没设对，回上表第 3 行。
⛔ 报一堆 `Sendable` / `actor-isolated` 之类的并发错误 → Swift 版本不是 5，回上表。

## 5. 装到手机上跑（关键验收）

1. 用线连上 iPhone，Xcode 顶部设备选**你的 iPhone**（不是模拟器）。
2. `Cmd+R`。
3. 手机上会打开 Caty，底部有 **三个 tab：首页 / 源 / 诊断**。先点 **「诊断」**。
   **第一次启动会慢一些**（要在设备上编译 + 建编译缓存），给它 **30～60 秒**。

### 应该看到（先看「诊断」tab）

| 位置 | 期望 |
|---|---|
| 状态 | 🟢 **已就绪**，右边有 `启动 x.xxs` |
| bridge 端口 | 5 位数（如 `52103`） |
| 服务地址 | `http://127.0.0.1:xxxxx`（和端口一致） |
| Node 版本 | `v24.20.0`（或 `v24.x`） |
| 架构 / pid | `arm64 / 12345` |
| 编译缓存 | 一段 `/var/mobile/Containers/…/Library/Caches/node-compile-cache` |
| 日志里 | `[stub] node=v24.x arch=arm64 WebAssembly=object fetch=function` |
| 日志里 | `serverStarted → http://127.0.0.1:xxxxx …` |
| 点「自检」 | `HTTP 200` + `{"app":"Caty","bridgePort":…,"ok":true,…}` |
| 点「读站点目录」 | `HTTP 200` + 里面有 `"name":"打桩站点"` |

### 再回到「首页」试播一次（P4 的验收，不用真源）

点 **「首页」** → 应该看到 **打桩站点** → 点进去 → 有 **打桩分类A/B** 两个分类胶囊、一条"打桩测试片" →
点进详情 → 有 **打桩线路/备用线路** 两条线路、两集 →
点 **第01集（直链）** 或 **第02集（走 ac=play）** → **画面应该出来**（Apple 官方测试流，彩色测试图）。

✅ 画面出来 = **A 方案（能播）达成**。
⛔ 黑屏但有声音 / 一直转圈 → 记下来告诉我（多半是编码或防盗链，见报错表 15–16 条）。

> `WebAssembly=object` 这一行很重要：它证明"无 JIT 也能跑 WebAssembly"，也就是 `fetch` 可用。

### 然后把这两样发我

1. 这一屏的**截图**（一张就够）。
2. 点 **「复制日志（已脱敏）」**，然后粘贴给我（脱敏是自动的，可以放心贴）。

## 6. 卡住怎么办（P2 专用；也可先查手册第 7 节的 20 条）

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 状态一直「启动中」，日志里**一行 `[stub]` 都没有** | NodeMobile 没真正跑起来：framework 没 Embed、或桥接头没设 | 回第 3、4 步；确认 `NodeMobile.xcframework` 是 `Embed & Sign` |
| App 一启动就闪退，日志里有 `FatalProcessOutOfMemory` 或 `VirtualMemoryCage` | V8 的指针压缩 cage 要一次性映射近 8 GB 虚拟地址，iOS 上部机型给不了 | 立刻把这行原文发我（要换构建参数） |
| 日志里 `WebAssembly=undefined` | 用了官方 Node 18.20.4 的包 | 换 `digidem` 的 `24.20.0-0` 包 |
| 日志里有 `[stub]` 输出，但一直没有 `serverStarted` | bundle 没拿到 `catServerFactory`（注入失败），或 `listen` 没被托管 | 把日志整段发我 |
| 90 秒后变成「失败：等待 serverStarted 超时」 | 首启太慢或上面几种情况 | 看日志最后几行；把整段发我 |
| 编译报 `Cannot find 'node_start' in scope` | 桥接头 / 链接没配好 | 回第 3、4 步 |
| 编译报 `multiple 'main'` / `'main' attribute` | Xcode 自动生成的 `CatyApp.swift` 没删 | 回第 2 步第 4 条 |
| 编译报 `Sendable` / `actor-isolated` 一类错误 | Swift 6 严格并发 | 回第 4 步：Swift 5 + Minimal |
| 真机上「不受信任的开发者」 | 免费账号证书没信任 | 手机 `设置 › 通用 › VPN 与设备管理 › 开发者 App` → 信任 |
| 想再点一次「启动」但按钮没了？ | 正常：iOS 上一个进程只能起一次 Node | 杀掉 App 重新打开即可（日志会保留在新的会话里） |

**通用原则**：报错 → **原文整段贴给我**（不要概括）。

## 附录 A · P3 验收（真源：下载 / 校验 / 缓存 / 多源）

代码已经在同一包里（`Sources/Runtime/BundleStore.swift`、`SourceRecord.swift`、
`RuntimeCoordinator.swift`、`Sources/Store/KeychainStore.swift`、`Sources/Features/Settings/SourceManageView.swift`）。
所以你不需要再拖文件，直接做下面的验收。

### A1. 导入一个真源

1. 手机上打开 Caty，停在 **「源」** tab。
2. 在输入框里粘贴你的订阅地址（形如 `http://user:pass@host/index.js.md5`；
   用电脑发到手机再复制，或直接在手机上输入）。也可以先复制好，再点 **「从剪贴板粘贴」**。
3. 点 **「导入」**。它会当场下载 6–9 MB 并做 MD5 校验，**等 10–60 秒**。

✅ 期望：列表里出现一条源，显示 `bundle xxxxxxxxxxxx`、`契约 contract-b-host-integrated`，
上面提示"导入成功……要重启 App 后才会加载"。
⛔ 报「下载失败」→ 看是否要代理；把文案发我。
⛔ 报「校验不通过，已丢弃本次内容」→ 把文案发我（可能是镜像站坏了或 MIME 伪装变了）。

### A2. 杀掉 App 重开 → 必须"缓存命中"

1. 从后台把 Caty 划掉（上滑关闭），重新点开。
2. 进 **「诊断」** tab 看日志。

✅ 期望：日志里出现 `store` 模块的一行 **`缓存命中（MD5 一致），不重新下载`**，
然后 `serverStarted → http://127.0.0.1:xxxxx`，`Node 版本 v24.x`。
**这是 P3 的核心验收**：重开不再拉那 6–9 MB。

### A3. 记录三个数字（D3 的关键产出，务必发我）

真源起来之后，在「诊断」tab 里记：

| 数字 | 在哪看 | 为什么重要 |
|---|---|---|
| **首屏耗时** | 状态右边的 `启动 x.xxs` | 决定"无 JIT 到底能不能用"（闸门指标） |
| **Node 版本 / 架构** | 「运行时」那几行 | 确认是 v24 线、arm64 |
| **是否崩溃** | 用 5 分钟，看会不会被系统杀掉 | 内存/cage 问题会在这里暴露 |

> 顺手把 `记忆` 也记一下：第二次启动（有编译缓存）的 `启动 x.xxs` 应该明显小于第一次 ——
> 那个差值就是编译缓存省下来的时间。

### A4. 多源与镜像（可选，1 分钟）

再导入一个**不同**的源 → 列表出现两条。如果两个源的 `bundle xxxxxxxxxxxx` 前 12 位相同，
说明它们是同一份 bundle 的镜像，日志里会写 **`是同一份 bundle（MD5 相同）→ 已记为镜像`**，
而且**不会重复下载**那 6–9 MB。

### A5. P3 专用报错

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 导入时卡很久后失败 | 源站慢/需要代理/302 到被墙的 OSS | 换镜像地址；把文案发我 |
| 「契约不支持」 | 这个包不是宿主集成型（contract-a，或标记不完整） | 换一个源（你的 4 个源实测都是 contract-b） |
| 导入成功但重开后仍是打桩源 | 源的开关被关掉了，或导入的那条 `enabled=false` | 「源」tab 里把开关打开，再重启 App |
| 重启后 Node 版本是 stub / 站点是"打桩站点" | 没导入源时 App 会故意跑打桩源 | 正常行为；导入并重启后会切到真源 |
| 想换源 | iOS 上一个进程只能起一个 Node | 关掉不用的源（开关），重启 App |
